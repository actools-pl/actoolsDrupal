## 0. Verdict and the one reframe that makes this cheaper

**Phase 0: NO-GO.** The LOCKED gate is not met. The install spine that actually runs (`actools.sh::setup_stack`, lines **569–1036**, 468 lines, 10 heredocs) is monolithic and profile-blind; the operator CLI is generated by a heredoc (`setup_cli`, line **1247**; `cat > /usr/local/bin/actools <<HELPER` at **1251**); the install-stage dispatcher the LOCKED stage model depends on (`run_install_stage` / `resolve_install_stage`) **exists in zero files**; and the resolver layer that *does* exist is **sourced but never called** on the live path.

**Can it be made canonical-modular? Conditional YES.** Nothing here is intrinsically un-modularizable. It is Bash; the seam primitives are sound; `modules/audit/*` already proves the team can factor cleanly; and the `init`/`preflight`/`doctor`/`handoff` surfaces are already extracted and tested.

**The reframe that lowers friction (and that the three reports under-state):** this is **not** a tangle to be untangled — it is a *deliberate, documented, half-finished migration with the second half scaffolded but switched off.* The repo's own `installer/dispatch.sh:19-20` says it outright:

> *"D.0 defining property: community installs see ZERO behaviour change. Resolver calls land in D.1+; D.0 establishes the seam only."*

Every one of the four surfaces carries the same literal comment — *"Resolvers are available for D.1+ … not called in D.0."* So the team shipped an intentional milestone ("D.0 = seam primitives + isolation tests, behaviour unchanged") and **explicitly deferred the wiring to "D.1+".** The LOCKED "Phase 0" is the **union** of both halves. Therefore the remaining work is *executing a scaffolded plan into sockets that already exist*, not reconciling rival philosophies. That distinction is what turns a scary refactor into a sequenced, low-risk wiring job.

## 4. Friction-reducers specific to *this* repo

The user's explicit ask. These are the levers that make the work lighter *here*, not generic advice.

1. **Strangle, don't rewrite.** Build the modular structure *around* the working monolith and prove byte-equivalence at every step. A big-bang rewrite of `setup_stack` + the CLI in one branch is the single most likely way to ship a broken installer.
2. **Split the scariest change in two (WP-2 before WP-3).** Introduce the dispatcher with handlers that *call the monolith unchanged* (zero behaviour change), then hollow the functions out behind it. This converts one high-risk structural move into a safe half and a guarded half.
3. **You are wiring into existing sockets, not laying new cable.** The sourcing is already in place in all four surfaces; `PROFILE_*` arrays **and their accessors** already exist (`profile.sh`); the dispatch functions, the `_ACTOOLS_DISPATCH_SOURCED` guard, and the `(community community-plus test)` allow-list already exist; the `test` fixture already models the contract; 76 tests already pass. The in-code **"not called in D.0 / lands in D.1+"** comments are a literal, author-written TODO map for WP-5.
4. **The golden harness is the universal de-risker.** Build it once (WP-1); reuse it in WP-2/3/4/5/6. It turns "did I change behaviour?" from a reviewer's judgment call into a CI result — which is what makes WP-3 tractable at all.
5. **Bank two cheap wins up front.** Standing up `design/` (build-trigger #2) and adding `actools.sh` to shellcheck are each <½ day, immediately shrink the contradiction surface, and satisfy real gate conditions. Do them in WP-0/WP-1 for momentum.
6. **Defer deletion to the very end (WP-8).** Keep the v9.2 orphans as *reference* during reconciliation; delete only on proof. This avoids Chesterton's-fence regressions and the DR breakage that naive deletion of `cli/actools`/`core/*` would cause (`resurrect.sh:153`, `lint.yml` shellchecks the orphans).
7. **One PR per WP (or per stage inside WP-3), each independently green and revertible.** Small blast radius, tractable review, and an exact match to the LOCKED "merged PRs + green CI" trigger.
8. **Make the credential ordering a hard, tested invariant.** Add a pre-render assertion that `DB_ROOT_PASS` is non-empty before any compose/my.cnf render, and pin the secret-gen→render order in a test. The file already carries `[fix4]/[fix7]` scars from this exact bug — encode the fix as a guard so the extraction can't reintroduce it.

## 5. Definition of done = the LOCKED build trigger

Phase 0 is complete (and the community-plus build unblocked) when **all** hold — this is also the canonical-modular acceptance set:

1. **One engine.** Host/stack/db/drupal/worker logic exists once; the inline `setup_stack` and the v9.2 `core/`+`host/`+`stack/` orphans do not both exist (WP-3/WP-8).
2. **One CLI, deployed not generated.** `/usr/local/bin/actools` comes from `cli/actools`; no behaviour lives only in the heredoc or only in the orphan (WP-4).
3. **The dispatcher is the only install path.** `main()` iterates `PROFILE_INSTALL_STAGES` via `run_install_stage`; `resolve_*` are *called* by live flows, not just defined (WP-2/WP-5).
4. **Community byte-identity is provable.** Golden fixtures show default `community` output is unchanged pre/post seam; a non-default profile fails cleanly on unknown checks (WP-1/WP-5/WP-6).
5. **One path semantics, one version string**, sourced from one place (WP-0/WP-7).
6. **Tests exercise the live path,** including the riskiest routine (today `setup_stack` ≈ 0% unit coverage), with byte-golden contracts on every generated artifact (WP-1/WP-3/WP-6).
7. **E2E installs both** the default and a loadable `test` profile and asserts each dispatch point fired (WP-6).
8. **Docs match code;** the §8 contradictions are closed; the false `cli/actools` comment is gone (WP-7).
9. **A published design-canon home exists** and is referenced from the tracker (WP-0) — the second LOCKED build-trigger condition.

When 1–9 are merged to `main` with green CI, flip the status and begin **LOCKED Phase 1 (Evidence Model)**.
