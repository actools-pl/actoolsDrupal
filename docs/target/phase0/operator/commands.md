# Command Surface — Target Contract

> **Status:** Phase 0 target contract — not yet released. This document describes intended
> behavior after Phase 0 seam hardening. It must not be treated as current released behavior
> until Phase 0 closure.

This document lists every command in the Phase 0 target command surface. For community
operators, the command surface is identical before and after Phase 0 seam hardening —
no commands are added or removed. The structural change is that `/usr/local/bin/actools`
is installed from `cli/actools` rather than generated by a heredoc.

---

## Installer commands (run as root via `actools.sh`)

These commands are run directly against `actools.sh` during initial setup.

| Command | Description |
|---|---|
| `sudo ./actools.sh init [flags]` | Create `actools.env`. See [install-community.md](install-community.md#stage-1--init). |
| `sudo ./actools.sh preflight` | Check server readiness. Exit `0`=ready, `1`=failures, `2`=warnings. |
| `sudo ./actools.sh install` | Full provisioning (alias for `fresh`). |
| `sudo ./actools.sh fresh` | Full provisioning (soft-deprecated in favour of `install`). |
| `sudo ./actools.sh handoff` | Print post-install summary panel. |
| `sudo ./actools.sh update` | Pre-snapshot → `docker compose pull` → `docker compose up -d` → `drush updb` → caddy reload. |
| `sudo ./actools.sh help` | Print help. Runs without sudo, env file, or lock. |
| `sudo ./actools.sh --version` | Print version string. Runs without sudo, env file, or lock. |

## CLI commands (run as the operator user via `actools`)

These commands are available after install via `/usr/local/bin/actools`.

### Common

| Command | Description |
|---|---|
| `actools doctor` | Daily health check: site, TLS, containers, DB, Redis, disk, backups, restore-test, Drupal bootstrap. Exit `0`/`1`/`2`. |
| `actools doctor --deep` | Gate stub — deep mode in development (community-plus Phase 1). Exit `2`. |
| `actools status` | `docker compose ps` — container status. |
| `actools logs [svc]` | Stream logs. Optionally for a named service. |
| `actools backup` | Run a backup now (calls `/etc/cron.daily/actools-backup`). |
| `actools update` | Pull latest images, run `drush updb`, reload Caddy. |
| `actools restart [svc]` | Restart a service or all services. |
| `actools drush <env> <cmd>` | Run a Drush command inside the named environment container. |

> **Note:** `handoff` is not a CLI command (`cli/actools` has no `handoff` case). It is
> available only as `sudo ./actools.sh handoff` (an installer mode). See
> [install-community.md — Stage 4](install-community.md#stage-4--handoff).

## Global CLI flags

The following flags are consumed by the CLI dispatcher before the command is dispatched:

| Flag | Description |
|---|---|
| `--profile <name>` | Override the active profile for this invocation. Must match the profile pinned in `actools.env` or the command fails with exit `2`. Conflict detection is fail-closed. |

---

## CLI authority (Phase 0 target)

After Phase 0 seam hardening, `/usr/local/bin/actools` is installed from `cli/actools`
(the static, canonical source). In the current codebase it is generated at install time
by a heredoc inside `actools.sh::setup_cli()`. The Phase 0 target collapses the two
implementations to one; command behaviour is identical.

See [`docs/architecture/cli-authority-contract.md`](../../architecture/cli-authority-contract.md)
for the full authority contract and CLI parity matrix.

---

## Profile resolution at runtime

On every `actools` invocation, the CLI:

1. Strips `--profile`/`--profile=VALUE` from `$@`.
2. Sources `actools.env` to load `ACTOOLS_PROFILE` (and other operational config).
3. Sources `installer/dispatch.sh` (provides `actools::cli::resolve_profile` and the
   resolver functions).
4. Calls `actools::cli::resolve_profile <cli_profile> <env_profile>` to resolve the
   active profile. Conflict between CLI flag and env-file value → exit `2`.
5. Exports `ACTOOLS_PROFILE` for the dispatched command to consume.

For `community`, every resolver returns empty, so the dispatched command receives no
override and runs its default community handler.

## Commands not in this surface

The following are intentionally not in the Phase 0 community command surface:

- `actools doctor --deep` real implementation (community-plus Phase 1)
- `actools audit --deep` (community-plus Phase 1)
- `actools evidence`, `actools verify`, `actools compliance`, `actools policy`,
  `actools approve`, `actools hardening-sync`, `actools adopt`, `actools baseline-create`
  (all community-plus Phase 1+)
