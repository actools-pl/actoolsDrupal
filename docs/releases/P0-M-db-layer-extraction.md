# Release note — P0-M · Stateful DB Layer Extraction (tests-first) + `wait_db` Hardening

Phase: P0-M (post-closure track) · Date: 2026-06-12 · `ACTOOLS_VERSION` unchanged at `14.0`

## What shipped

1. **Contract/mock tests for the DB layer** (`tests/db/`, 13 tests). The six
   DB functions are stateful — they exec against a live MariaDB container —
   so there is no rendered output to golden-capture. Behavior is pinned by a
   mock `docker` on PATH that records every invocation's argv (NUL-separated;
   the `sh -c` bodies are multi-line) and stdin: the tests assert the exact
   commands and SQL each function issues, including the least-privilege
   backup-user grant and `wait_db`'s 50×3s bounded polling. An auto-locating
   loader ran the same assertions against the inline code first and the
   extracted module after — the faithfulness proof across the move.

2. **The six DB functions extracted verbatim** from `actools.sh` into
   **`modules/db/core.sh`** (live module, `LIVE AUTHORITY (P0-M)` header):
   `db_exec_root`, `db_exec_root_stdin`, `db_dump_container`,
   `setup_backup_db_user`, `wait_db`, `check_db_creds`. Per-function
   byte-identity verified; `actools.sh` went 763 → 690 lines (the `:450-530`
   region became a banner + one `source` line at the same spot); every call
   site untouched. Golden drift 6/6 and the backup-cron fixture held at every
   commit — the DB layer generates no files.

3. **The stale v9.2 twins retired**: `modules/db/{backup_user,credentials,
   wait}.sh` deleted. They were unwired orphans whose content diverged from
   the live v14 code (a different `check_db_creds` message; a `wait_db`
   carrying the argv-password probe). Their content was never adopted;
   grep-proof shows zero references on any `.sh`/`.yml`/`.bats` surface.

4. **The duplicate-function guard extended** to the six DB names — closure
   exactly-once, wired-twin, and (post-retirement) the unconditional
   `modules/db` twin ban. Non-vacuity demonstrated twice: wiring the stale
   `wait.sh` twin at commit-2 state failed two arms; a reintroduced inline
   `wait_db(){ :; }` at end-state failed all three. The stale twins cannot be
   re-wired or restored without failing CI.

5. **`wait_db` hardened — the one intentional behavior change** (isolated
   final implementation commit). The readiness probe previously ran
   `mariadb -uroot -p"${_wp}"` inside `docker compose exec` — the DB **root**
   password on argv, visible to every local user via `ps` (the Entry-017
   known risk at `actools.sh:510`). The probe now mirrors the backup-cron
   pattern: the printf builtin pipes a `[client]` defaults file into a
   **umask-077 temp file inside the container** and the client runs
   `mariadb --defaults-extra-file="$t"`. No process on the host or in the
   container ever carries the password on argv. The probe SQL (the
   `mysql.actools_write_check` write-check), the 50-try/3s bounds, and the
   log/error lines are unchanged — same outcome, different auth method.
   Locked in CI by `tests/guards/wait_db_security_guard_test.bats`
   (non-vacuous: the retired argv form demonstrably fails it).

## Operator impact

None expected. Install logs are identical; no generated byte changed; the
CLI is untouched. The only observable difference is in `ps` output during
the DB-readiness window: the root password no longer appears.

## Gate status

The hardening is **e2e-gated**: the CI fresh-install e2e (`e2e.yml`) must
confirm the install still reaches DB-ready. Mock-level outcome equivalence
and the container-side temp-file mechanics are proven in the test report;
the real-install confirmation could not run in the coding sandbox (no docker
daemon / cloud token) and is the Review Gate's remaining item. The hardening
is the isolated final implementation commit and can be dropped without
touching items 1–4 if the e2e fails — the spec's split rule.
